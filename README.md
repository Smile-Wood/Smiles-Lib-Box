# Smile's Lib Box

[中文文档](README.zh-CN.md)

A cross-version prerequisite library with two responsibilities: it collapses "which game version is this, and which capabilities does it have" into one fixed API; and it compiles the Minecraft interfaces that change between versions (Screen override signatures, key-mapping factories, input events, narrator, contextual-bar injection) into per-version adapter layers that dependents can call.

The skeleton was generated by the official Fabric CLI (`fabric init`). Artifacts are published per version:
`smile_libbox-1.0.26+1.20.1.jar` … `+1.21.11.jar` (eight jars, one per game version), plus a `+26.2.jar` assembled by a
separate script (26.2 has no intermediary — see "Build and install"). There is deliberately no version-agnostic jar:
the adapters under `smile_libbox.client.compat` / `mixin` are compiled against their own version's MC jar and their refmaps
come from it too, and `depends.minecraft` is `~<version>`, so the loader rejects a mismatched jar up front instead of
failing later at runtime. Nothing under `smile_libbox.api` references a `net.minecraft.*` type (verified against the class
constant pools), so that part is one set of classes usable on every version — which is what lets a dependent mod ship a
single jar. At install time pick the jar matching the game version and put it in `mods/`.

---

# For mod authors: deciding the version

This section is for **authors who depend on this library**. You do not need to publish one jar per game version, and you do not need conditional compilation such as Stonecutter. Two steps are enough: determine version / capability, then load the matching implementation.

## 1. Pick the right criterion first

| What you want to know | Which API | Example |
| --- | --- | --- |
| Game version range | `GameVersion` / expressions | `GameVersion.atLeast("1.21.9")`, `Conditional.matches(">=1.21.9")` |
| Data pack format version | `MinecraftVersions` | `dataPack()`, `dataPackMinor()`, `dataPackAtLeast(15, 0)`, `Conditional.matches("datapack:>=15.0")` |
| Resource pack format version | `MinecraftVersions` | `resourcePack()`, `resourcePackMinor()`, `resourcePackAtLeast(75, 0)`, `Conditional.matches("resourcepack:>=75.0")` |
| Protocol / world data version | `MinecraftVersions` | `protocol()`, `world()`, `protocolAtLeast(763)`, `worldAtLeast(3465)`, `protocol:>=763`, `world:>=3465` |
| Game version / Java version | `MinecraftVersions` | `game()`, `name()`, `java()`, `summary()` |
| Whether an ABI capability exists | `Compat` / `cap:` | `Compat.eventBasedInput()`, `Conditional.matches("cap:dataComponents")` |
| Whether a mod / class is present | `ModPresence` / `mod:` `class:` | `ModPresence.loaded("vanillabackport")`, `class:net.minecraft.client.KeyMapping$Category` |
| Several conditions at once | `Conditional` | `Conditional.matches(">=1.21.9 & mod:vanillabackport")` |

**Prefer capability / data-version checks over game-version checks.** Modpacks frequently ship backport mods that move high-version features onto older versions, and snapshot version numbers are not monotonically numeric. Testing "data pack format >= 15" or "class X exists" usually tracks the API you actually call more closely than "game version >= 1.20.5".

All values come from `version.json` at the root of the client jar (read with the JDK only — zero MC dependencies). Before 1.21.9 `pack_version` is `{"resource":15,"data":15}`; afterwards it becomes `{"resource_major":75,"resource_minor":0,"data_major":94,"data_minor":1}`. This library **normalises both shapes into major + minor**, filling minor with 0 for the old shape, so you never need to branch:

| Environment | Game | Data pack | Resource pack | Protocol | World | Java |
| --- | --- | --- | --- | --- | --- | --- |
| 1.20.1 | `1.20.1` | `15.0` | `15.0` | 763 | 3465 | 17 |
| 1.21.11 | `1.21.11` | `94.1` | `75.0` | 774 | 4671 | 21 |

Condition expressions fully support: `*` or empty, `>=1.21.9`, `>1.20.1`, `<1.20.2`, `<=1.21.8`, `==1.21.11`, `!=1.20.1`, `mod:xxx`, `!mod:xxx`, `class:xxx`, `cap:xxx`, `datapack:>=15.0`, `resourcepack:>=75.0`, `protocol:>=763`, `world:>=3465`
(the last four accept `>= > <= < == !=`). Join with `&` to require all of them.

## 2. Cheat sheet of the boundaries that matter

Once you know the version, what do you change? The table below lists the boundaries between 1.20.1 and 1.21.11 that genuinely change compilation signatures. `Compat` exposes each of them as a fixed boolean, so you do not have to memorise version numbers:

| Boundary | Change | How to test |
| --- | --- | --- |
| 1.20.2 | `renderBackground` gains window arguments; `mouseScrolled` gains a horizontal component | `Compat.fourArgBackground()` / `cap:fourArgBackground` |
| 1.20.5 | Item stacks move to DataComponent; the NBT read/write API is replaced wholesale | `Compat.dataComponents()` / `cap:dataComponents`; for content-related logic prefer `datapack:` |
| 1.21 | `ResourceLocation` construction becomes static factories | `Compat.resourceLocationFactory()` / `cap:resourceLocationFactory` |
| 1.21.5 | `Narrator.say` gains a volume argument | `Compat.narratorVolume()` / `cap:narratorVolume` |
| 1.21.9 | Input callbacks become event objects, key categories become objects, resource class names change, the bar above the hotbar becomes the contextual bar | `Compat.eventBasedInput()` / `cap:eventBasedInput`, `Compat.contextualBar()` |
| 1.21.9 | `pack_version` becomes `*_major` / `*_minor` | No test needed — `MinecraftVersions` normalises it |

## 3. Keeping a dependent mod as a single jar

> **Precondition**: the "split classes + lazy loading" technique below only works **within one namespace generation** (the intermediary generation, 1.20.1–1.21.11). From 26.x on, Mojang ships official names, the compile-time class names differ, and lazy loading cannot bridge that gap.
> To keep **the consumer** a single jar across generations, use the approach this library now uses: confine every MC type to a per-generation adapter layer, and let the main jar depend only on the pure-Java contract in `smile_libbox.api.ui`
> (`Ui` / `UiScreen` / `UiCanvas` / `UiHost` / `ConfigSpec` / `KeyRef`), with zero `net/minecraft` references in the constant pool; the library publishes one jar per namespace that supplies the `Ui.Backend` implementation.
> This has been verified on a real 26.2 modpack — see "Verification record".

**Why you cannot simply write both overrides**: before 1.21.9 `Screen#keyPressed` is
`keyPressed(int, int, int)`; afterwards it is `keyPressed(KeyEvent)`, and `KeyEvent` does not exist on 1.20.1.
A single class cannot hold both signatures, and build-time conditional compilation only gets you multiple jars.

**What does work**: a jar is just a container and JVM class loading is lazy, so a class name held in a string produces no symbolic reference.

1. Split implementations that only work on a version range into **separate classes**, each in its own package;
2. Let the main flow depend on one **stable interface** (defined by you, with no MC types in its signatures);
3. At runtime evaluate `Conditional`, and only on a hit call `Class.forName` and instantiate;
4. Classes whose condition never holds are never loaded, so they cannot throw
   `NoClassDefFoundError` for referencing absent types; all implementations still ship in **one jar**.

Class layout:

```
mymod/
  MyMod.java                       ← references only the stable interface, never imports version-bound classes
  api/BarHooks.java                ← stable interface; signatures use JDK / library types only
  compat/legacy/LegacyHooks.java   ← implementation for < 1.21.9, may reference old types
  compat/v1219/ModernHooks.java    ← implementation for >= 1.21.9, may reference KeyEvent etc.
```

Copyable pattern:

```java
// Stable interface: no MC types anywhere in the signatures
public interface BarHooks {
    void onTick();
    boolean wantsLocatorBar();
}

// Entry point: string class names only
public final class MyMod implements ModInitializer {
    private static BarHooks hooks;

    @Override public void onInitialize() {
        hooks = Conditional.choose(BarHooks.class,
                ">=1.21.9              => mymod.compat.v1219.ModernHooks",
                "mod:vanillabackport   => mymod.compat.backport.BackportHooks",
                "*                     => mymod.compat.legacy.LegacyHooks");
        // One-shot actions can also be executed conditionally
        Conditional.when(">=1.20.5", "mymod.compat.v1205.ComponentSetup");
    }
}

// Feature switches / visibility of config rows: pure predicates
if (Conditional.matches(">=1.21.9")) {
    // show options that only exist on newer versions
}
```

`choose` takes the first rule whose condition holds, top to bottom, and returns an instance of the stable interface. Implementation classes need a public no-argument constructor (the library calls `setAccessible(true)`). Any load or instantiation failure is logged and yields `null` — the game never crashes. Single actions can use `when(expr, className)` or `run(className)`; the implementation implements
`Conditional.Action` or `Runnable`.

**Mixins are gated by the mod itself, too**: extend `VersionedMixinPlugin`, write the rules in `accepts()`, and put your subclass name in the mixin config's `"plugin"` field. When it returns false the mixin class is skipped before it ever reaches the parsing stage.

```java
public final class MyMixinPlugin extends VersionedMixinPlugin {
    @Override protected boolean accepts(String target, String mixin) {
        if (mixin.contains(".compat.v1219.")) return matches(">=1.21.9");
        if (mixin.contains(".compat.legacy.")) return matches("<1.21.9");
        return true;
    }
}
```

The library's own `LibBoxMixinPlugin` works exactly this way (gating ABI clusters by the `.v1201.` / `.v1202.` / `.v1215.` /
`.legacy.` / `.modern.` package-name fragments).

One pitfall that only shows up in a real environment: the development classpath contains **two copies of
`version.json`, one from clientOnly and one from common**, and other jars may ship the same resource name too. `MinecraftVersions` picks the copy whose id matches what the Loader reports; do the same filtering when you read the resource yourself.

**Offline probe**: using a single `version.json` to switch the simulated environment, the same probe (containing a type that "only exists in 1.21.9") showed:

- **1.20.1**: `matches(">=1.21.9") = false` → `choose` returns the fallback implementation; the static initialiser of the newer implementation class **never runs**, and even though the simulated new type is absent from the classpath there is no `NoClassDefFoundError`;
- **1.21.11**: `matches(">=1.21.9") = true` → the newer implementation loads and resolves that new type successfully.

The real `version.json` files from both versions also validated `dataPackAtLeast` / `resourcePackAtLeast` /
`protocolAtLeast` / `worldAtLeast` and the `datapack:` / `resourcepack:` / `protocol:` /
`world:` expressions: for example `datapack:>=94.1` is false on 1.20.1 and true on 1.21.11, and likewise for
`resourcepack:>=75.0`, `protocol:>=774`, `world:>=4671`.

In other words, "split classes + lazy loading" **does** hold for ordinary classes within the same namespace generation.
Mixin refmaps and cross-generation compile-time class names cannot be solved by runtime checks;
for cross-generation work use the pure-Java `smile_libbox.api.ui` facade plus per-generation library jars, as described in
"Notes for authors" and "Build and install".

# Letting the mod decide whether to inject (including integration with other mods)

**Conclusion first**: the decision belongs 100% to the **consuming mod**. The library supplies the criteria and the gating base classes; it never decides on its own whether a given mixin should apply. The consumer, inside its own single jar, uses the current game version, capabilities and installed mods to decide "should this version inject at all" and "which injection class to use". The only exception is when the **injection method descriptor contains MC types** — then the injection class must be compiled by the library per version. Whether to use it still belongs to the consumer's plugin.

## Channel 0: gate your own mixins by version (most common)

The decision happens at **mixin config parsing time**, not at game runtime: extend `VersionedMixinPlugin` and mixin classes for which
`accepts()` returns false **are never parsed at all**, so they cannot blow up even if they reference types missing from the current version. The criteria can only be pure-Java data (`version.json`, classpath resources, the Loader mod list), because at this stage MC classes are not loaded yet.

```java
public final class MyMixinPlugin extends VersionedMixinPlugin {
    @Override protected boolean accepts(String target, String mixin) {
        if (mixin.endsWith("LegacyBarMixin")) return matches("<1.21.9");
        if (mixin.endsWith("ModernBarMixin")) return matches(">=1.21.9");
        if (mixin.endsWith("BackportMixin"))  return matches("mod:vanillabackport");
        return true;
    }

    // You can also append mixin classes dynamically per version and leave the config's client array empty
    @Override public List<String> getMixins() {
        return matches(">=1.21.9")
                ? List.of("mymod.client.mixin.ModernBarMixin")
                : List.of("mymod.client.mixin.LegacyBarMixin");
    }
}
```

`getMixins()` returns class names **appended** to the config (relative to `package`); combined with
`required: false` + `defaultRequire: 0`, names that do not match the version never reach the parse queue.
`VersionedMixinPlugin` pins `getRefMapperConfig()` to `null` and swallows every exception while logging it.

```json
{
  "required": false,
  "package": "mymod.client.mixin",
  "compatibilityLevel": "JAVA_17",
  "plugin": "mymod.client.mixin.MyMixinPlugin",
  "client": [],
  "injectors": { "defaultRequire": 0 }
}
```

**Two hard boundaries**:

- Do not put the decision inside the mixin method body (`if (GameVersion.atLeast("1.21.9")) ...`).
  By then the class is already parsed, and a mismatched injection descriptor fails outright; `require = 0` only makes it fail silently,
  it cannot make it "apply per version". The decision must happen in `shouldApplyMixin()` (before parsing).
- When spanning 1.20.1 (intermediary) and 26.2 (named), a mixin class containing MC types
  **cannot carry both descriptor sets in one jar**. Use Channel B for that case; only soft-target mixins whose descriptors contain no MC types can stay in a single jar and be gated by the consumer.

The following discusses only integrations whose **target is not an MC class**; gating follows Channel 0, and the business decision always goes through the callbacks of
`smile_libbox.api.link.ModLinks`. The library never grows an extra jar just to enable an integration — integrations are split by **MC namespace generation**, not by "third-party mod".

| Ask yourself first | Conclusion |
| --- | --- |
| Does the third-party mod expose a public API / event? | Call it reflectively, zero mixins (`BackportBridge` is a read-only example) |
| You need to inject, and the target descriptor **contains no MC type**? | **Channel A**: the consumer's single jar owns the thin injection and registers callbacks |
| The descriptor contains MC types (`GuiGraphics` / `PoseStack` / `Player` …)? | **Channel B**: the library compiles the integration mixin per version; the consumer only registers callbacks |
| Several consumers need the same injection point? | Always Channel B, so that duplicate injections cannot overwrite each other |

Key point: a third-party mod's **class names are not** `net/minecraft/*`. `@Mixin(targets = "...")` with
`remap = false` does not participate in refmaps, so the target class name is stable across intermediary and named generations; what actually breaks is the
**parameter / return descriptors** in `method = "..."`. Injection points like `shouldSkipRendering()Z` — no arguments, primitive return — are safe;
`render(GuiGraphics, float, ...)` looks different in all three namespaces (1.20.1, 1.21.9, 26.2) and must be compiled by the library per version.

## Channel A: the consumer's single jar owns the injection point (recommended)

toolb's VanillaBackport integration uses exactly this path, across four files:

**1. Thin injection class** — dispatches once, imports neither the config class nor the target mod's business classes:

```java
@Mixin(targets = "com.example.backport.client.LocatorBarRenderer", remap = false)
public abstract class MyBackportMixin {
    private static final String HOOK = "example.locator_bar.skip";

    @Inject(method = "shouldSkipRendering()Z", at = @At("RETURN"),
            cancellable = true, remap = false, require = 0)
    private void mymod$choose(CallbackInfoReturnable<Boolean> cir) {
        Boolean value = ModLinks.dispatchBoolean(HOOK, cir.getReturnValue());
        if (value != null) cir.setReturnValue(value);
    }
}
```

**2. Gating plugin** — extend the library's `SoftTargetMixinPlugin`; declare only "whom we integrate with":

```java
public final class MyBackportPlugin extends SoftTargetMixinPlugin {
    protected String modId() { return "examplebackport"; }
    protected String[] markerClasses() {
        return new String[]{"com.example.backport.client.LocatorBarRenderer"};
    }
    // Optional: protected String when() { return ">=1.20.1"; }
}
```

The base class checks, in order, `Conditional.matches(when())` → mod id → every marker class; when the Loader is not ready yet at this very early stage, marker classes are additionally probed as classpath resources. It pins `getRefMapperConfig()` to `null` (soft targets are not remapped).

**3. Mixin config** — a separate file, `required: false`, `defaultRequire: 0`:

```json
{
  "required": false,
  "package": "mymod.client.mixin",
  "compatibilityLevel": "JAVA_17",
  "plugin": "mymod.client.mixin.MyBackportPlugin",
  "client": ["MyBackportMixin"],
  "injectors": { "defaultRequire": 0 }
}
```

Register it as a separate entry in `fabric.mod.json` with `"environment": "client"` — do **not** put it in the main config.

**4. Business callback** — a plain Java class registered from the client entry point:

```java
public final class MyBackportLink {
    public static void register() {
        ModLinks.onOverride("example.locator_bar.skip", MyBackportLink::choose);
    }
    private static Object choose(String hook, Object original) {
        // original is the third-party mod's own return value; return null = do not interfere
        return MyConfig.get().forceBar ? Boolean.TRUE : null;
    }
}
```

`ModLinks` supports multiple subscribers per hook (the first non-`null` override wins, in registration order),
`emit(hook, payload)` for notification-style hooks, `active(hook)` / `subscribers(hook)` so the config screen can show
"integration active", and `describe()` for a one-line startup self-check. Callback exceptions are isolated one by one and never break the third-party mod's method. The `HOOK` literal in the injection class must match the string used for callback registration — that is the only contract
across the jar boundary, and it creates no compile-time symbolic reference.

## Channel B: when the descriptor involves MC types, hand it to the library

There is exactly one reason to place it on the library side: a mixin's `method` descriptor is decided by the **MC jar used at compile time**, and
`remap = false` does not save you. The library already publishes per version, so each jar can carry an integration injection class with the matching descriptor, and the consumer's code needs no change (hook ids stay the same).

Where things go:

1. `src/client/java/smile_libbox/client/mixin/LibExampleMixin.java`, compiled against that Stonecutter
   node's MC, with the refmap generated by Loom; the body again only calls `ModLinks.dispatch(...)`.
2. Add `src/client/resources/smile_libbox.example.mixins.json` (`required: false`,
   `defaultRequire: 0`, plugin `LibBoxMixinPlugin` or a `SoftTargetMixinPlugin` subclass),
   and append an entry to the `mixins` array in `src/main/resources/fabric.mod.json`.
3. 26.2 official-name generation: write a same-named class under `named26/src/smile_libbox/client/mixin/` (official-name descriptors),
   add the class name to `named26/resources/smile_libbox.named26.mixins.json`;
   append the lower-version config name to `DROP_EXACT` in `tools/build_named26.py`, append the 26.2 config to the
   `mixins` list in `metadata()`, and add the new class to the `required` set in `verify()`.
4. Besides checking whether the target mod is loaded, the plugin should use `libbox-target.txt` to verify that the installed jar matches the version,
   so a wrong library version cannot weave mismatched descriptors into the game.

**The library should not know arbitrary third-party mods in advance**: only integrations that are "shared by several consumers" or "have MC types in the descriptor" belong in the library; everything else goes through Channel A. The library also cannot depend on a consumer's config classes, so an integration injection class may only reference
`ModLinks` and mixin annotations.

## Channel C: player / world / outbound packets (World & Packets)

`smile_libbox.api.world` is the second facade, for mods that need to act on the client. Like `api.ui`
it is pure Java: items are registry-name strings (`"minecraft:elytra"`, `"minecraft:mace"`),
coordinates are `double[]` / `int`, and MC entities never appear in a signature. When no implementation is installed (`ready()==false`)
or there is no player, everything returns safe defaults, so callers never need null checks.

### World: state + three actions

| Purpose | Methods |
| --- | --- |
| Position / motion | `pos()` / `motion()`, returning `double[]{x,y,z}` |
| Ground / fall / sneak / glide | `onGround()` / `fallDistance()` / `sneaking()` / `gliding()` |
| View pitch | `pitch()`: degrees, `-90` up, `+90` down. While gliding, the sneak key is vanilla's "look down to dive faster"; distinguishing "slow down" from "slam down" is only possible from the view angle |
| Distance to ground | `groundDistance()`: the top face of the first solid block below, searching 48 blocks down by default, returning `Double.MAX_VALUE` if nothing is found; `groundDistance(n)` sets the scan depth (slam attacks from tens of blocks up need it) |
| Chest slot | `chestItem()` / `chestIsElytra()` |
| Hotbar | `hotbarSlot(id)` / `selectedSlot()` / `selectSlot(i)` |
| Change armour | `equipChestArmor()`: sends the elytra back to the inventory and equips the strongest piece there (enchantment count first, then max durability) |
| Mace | `maceInInventory()` / `maceToHotbar()` (picks the one with the **highest density level**; switches slots if already on the hotbar, otherwise sends a container-click packet to move it) |
| World | `isSolid(x,y,z)` / `nearbyLiving(r)` / `attackNearest(r)` |
| Entity snapshot | `entities(r)`: `EntityView[]` for every `isPickable()` entity in range (registry name, foot position, velocity, bounding box, whether it is a living entity). Boats and armour stands are included; item entities, arrows and experience orbs are not. `attackNearest(r)` prefers living entities and only hits boats and armour stands when none are present |
| Screen | `containerOpen()`: distinguishes "the player clicked in their own inventory" from "the mod swapped automatically" |

`EntityView` is a pure-Java value object (see `smile_libbox/api/world/EntityView.java`) that flattens entities into
numbers, so dependents can do geometry such as impact prediction, and can run self-tests outside the game. `World.Backend#entities`
has a default implementation (returning an empty array), so third parties implementing `Backend` themselves are not blocked by new methods.

Version differences are all confined to the adapter layer: `Inventory.selected` became private in 1.21.5 → use `getSelectedSlot()`;
`Entity.fallDistance` became `double` in 1.21.11 → uniformly narrowed; `getEquipmentSlotForItem`
moved from static to instance in 1.21; `Level#getEntitiesOfClass` was removed in 26.2 → use `getEntities(except, aabb, predicate)`.

### Packets: black-box interception of outbound container actions

Consumers never touch `ServerboundContainerClickPacket` / `ClickType` / `ContainerInput`; they register one rule:

```java
Packets.addRule(action ->
        armorLocked && action.chestSlot && "minecraft:elytra".equals(action.itemId));
```

The library evaluates at the `HEAD` of the client's central packet-send entry point (intermediary's
`MultiPlayerGameMode#handleInventoryMouseClick`, 26.2's `handleContainerInput`) and cancels on a hit — **the packet is never sent and no local prediction happens**, so the screen does not jitter.

`Action` exposes `kind` / `containerId` / `slot` / `button` / `clickType` / `itemId` /
`chestSlot` / `armorSlot`. A rule that throws is treated as "allow", so one bad rule cannot break every inventory action.

## Hard constraints checklist

- **`remap = false` + no refmap**: the target class belongs to a third-party mod, so going through Loom's refmap would remap it
  by MC names and get it wrong. `SoftTargetMixinPlugin` already pins `getRefMapperConfig()` to `null`.
- **`required: false` + `require = 0` + a separate config**: omit any one of the three and the game crashes when the target mod is absent.
  Gating must happen in `shouldApplyMixin()` (before parsing); `preApply` is already too late.
- **`compatibilityLevel` must cover the target class's class-file version**: 26.2 game classes are class 69, so the library's
  named config uses `JAVA_25`; a consumer single jar that hardcodes `JAVA_17` only works when the target class itself comes from a
  third-party mod built for Java 17 or below. mixin 0.8.7 supports up to `JAVA_25`.
- **Zero `net/minecraft` references in the injection class constant pool**: otherwise "single jar across generations" breaks immediately. Verify with
  `javap -v` or a constant-pool scan; parameters such as `CallbackInfoReturnable<Boolean>` that contain only JDK types are safe.
- **Do not import the target mod's classes in the injection class**: `@Mixin(targets = "string")` is enough; once a
  compile-time symbolic reference exists, the class cannot even be parsed when the target mod is absent.
- **Cache probe results**: `ModPresence` / `ModLinks` queries are cheap, but a third-party mod's reflection bridge
  (`BackportBridge`) should resolve only once and fall back to the safe "do not interfere" value on any failure.
- **Use lowercase dot-separated hook ids** (e.g. `vanillabackport.locator_bar.skip`); the bus lowercases with
  `toLowerCase(Locale.ROOT)` before matching, so mismatched case never silently stops callbacks.

# Example: chat draft (library-side injection + consumer-side persistence)

Requirements like "keep what was typed after closing and reopening chat, keep it when rejoining the server shortly after, keep it across clients logging in with the same account, and key everything by server address" are a good demonstration of **how to layer things when the descriptor involves MC types**:

| Layer | Responsibility | Location |
| --- | --- | --- |
| Injection point | Read / write `EditBox`, turning `init()` / `removed()` / `handleChatInput` into fixed callbacks | library-side `LibChatDraftMixin`, compiled once per version jar |
| Event bus | Pure-Java `ChatDraftEvents.onCapture` / `onRestore` | `smile_libbox.api.event` (base jar, shared across generations) |
| Business rules | Key by server address, TTL, persistence, clearing policy | consumer single jar (toolb's `ChatDraftStore`) |

**Version differences** (verified per version with mappings / `javap`):

| Generation | `ChatScreen#handleChatInput` | Other injection points |
| --- | --- | --- |
| 1.20.1 / 1.20.4 | `(String,boolean) boolean` → `CallbackInfoReturnable<Boolean>` | `init()V` / `removed()V` / `@Shadow EditBox input` |
| 1.20.6 – 1.21.11 | `(String,boolean) void` → `CallbackInfo` | as above |
| 26.2 named | `(String,boolean) void`, descriptor written with official names, no refmap | as above; vanilla additionally has an in-session draft via `ChatComponent#saveAsDraft` |

Stonecutter uses `//? if >=1.20.6` to switch the injection method whose return type differs; Loom rewrites the other two
injection points to `method_25426()V` (init) and `method_25432()V` (removed), and
`@Shadow input` to `field_2382:Lnet/minecraft/class_342`. The 26.2 copy has no refmap, so the
annotations keep `init()V` / `removed()V`.

**How the three scenarios are each handled**:

1. Close and reopen → `removed()` hands the text to `dispatchCapture`, and the next `init()` refills it via
   `dispatchRestore`.
2. Rejoin shortly after disconnecting → the consumer decides whether the draft has expired based on TTL; TTL is measured from the last `removed()`.
3. Logging in from another client → the consumer writes the draft to the **user home directory** rather than `gameDir/config`,
   so another client instance reads the same file; the key is `Ui.serverAddress()` (the `ServerData.ip` the player entered),
   not the player name / world name / client instance.

On message submission `handleChatInput` calls `dispatchCapture(address, "")`, and the consumer deletes the draft for that address so it does not reappear next time.

**Clearing alone is not enough**: vanilla `handleChatInput` only sends the packet and does **not** clear the
`EditBox` (the 1.20.1 bytecode is `iconst_1 / ireturn`, 1.21.11 is `return`); only afterwards does `keyPressed` call `setScreen(null)`,
so inside `removed()` `input.getValue()` is still the line that was just sent, and the draft is stored again verbatim — the symptom being
"after sending with Enter, reopening chat still shows the previous message". 1.21.x vanilla avoids this with
`exitReason == DONE` (`shouldDiscardDraft()`), but 1.20.x has no such field, so the library uniformly remembers the submitted text in an
`@Unique` field: if the content is unchanged in `removed()` it is treated as "closed after sending" and not persisted; commands sent by other mods
(with arguments differing from the box content) are not recorded, so a draft the player had not finished is never deleted by mistake.

26.2 vanilla has its own in-session draft, so `init()` refills only when the box is **empty**, never overwriting what vanilla just saved.

# Debug actions (`smile_libbox.api.debug.Debug`)

A generic facade for external AI agents / test tooling: `Debug.call(action, args)`, where arguments and return values use JDK types only.
Supported actions: `describe` / `screen` / `click` / `key` / `type` / `scroll` / `player` / `entities` /
`world` / `block` / `inventory` / `target` / `command` / `close_screen` / `place_block` /
`use_block` / `use_item` / `container` / `click_slot` / `keybind` / `keybinds` — all one-shot actions that run
**only when explicitly invoked**.

**Removed: `control` / `move` / `mine` / `job` (player-driving actions)**. To let an AI "hold a direction key and walk", the old implementation
registered a per-frame callback in the constructor and wrote virtual state straight into the `isDown` of eight `KeyMapping`s such as
`options.keyUp` / `keyJump` / `keySprint` — with an empty virtual table that amounts to **resetting every real key to released on every tick**.
26.x samples input from `KeyMapping` per frame, and `KeyMapping.setDown` only writes `isDown` without touching `clickCount`,
so holding forward / sprint looked fine (the physics state was replayed), while an edge-triggered action like jump, landing in that window, was
read as released — presenting as "one jump press instantly brakes". Those four actions now return an explicit error, and the library no longer
contains any code that rewrites input state per frame; to drive the character, use vanilla commands or external key injection.

# Notes for authors

- **This library does not adapt arbitrary MC interfaces for you.** When a signature changes, follow section 3: split the per-version implementations into
  separate classes and define your own stable interface; no library can pre-declare interfaces for every mod. The library pre-declares only one
  **general GUI / input / narrator facade**, `smile_libbox.api.ui`, for "single-jar consumers" across namespaces (toolb uses it).
- **Check the namespace generation before the version**: this is the **first dividing line** for "can a mod depending on this library stay a single jar", and it outranks every version check. Official 1.20.1–1.21.11 environments use
  intermediary (`net/minecraft/class_304`), remapped by the Loader with mappings;
  from 26.x on Mojang publishes official names directly (`net/minecraft/client/KeyMapping`),
  the launch log shows `Mappings not present!`, and every other mod in the pack no longer carries
  `class_*` references. **A single class file cannot cross that boundary**: class names are baked into the constant pool at compile time,
  and neither `Conditional` lazy loading nor `Compat` reflection changes that.
  How to tell: look for `net/minecraft/class_310.class` versus `net/minecraft/client/Minecraft.class` in the client jar, or check whether the launch log contains `Mappings not present!`.
  To cover both generations, **the library compiles one jar per generation** (`+1.20.1`–`+1.21.11` via Stonecutter/Loom,
  `+26.2` via `tools/build_named26.py` calling javac directly with official names),
  and **the consumer isolates all MC types into a per-generation adapter layer, keeping the main jar's constant pool free of `net/minecraft`**,
  depending only on `smile_libbox.api.ui`. This path is verified on a real 26.2 instance.
  Note that `com.mojang.blaze3d.platform.InputConstants` is also remapped in production to
  `net/minecraft/class_3675`, so use `KeyRef` rather than `InputConstants.Key`.
- **A mixin's injection target is decided by the compile-time refmap**: in the intermediary generation production method names are
  `method_xxxxx`, and the refmap is generated from whichever MC version you compiled against. `VersionedMixinPlugin`
  can only decide "should this mixin be used"; **it cannot change the injection descriptor**. If your mixin must apply across ABI clusters,
  compile that cluster's mixin class against the matching MC jar per cluster and merge the classes into one jar
  (you merge classes; the artifact is still one jar), then gate them with the plugin. Across namespace generations this is equally ineffective.
- **Find methods by shape, do not hardcode names**: production runs in the intermediary namespace, and
  `Compat.findMethod(owner, argCount, returnType, nameCandidates...)` can locate by argument count / return type alone;
  `findByShape` locates by parameter-type shape; `call` returns `null` on failure; `intOf` / `doubleOf`
  read field-style accessors reflectively from event objects.
- **Class-loading conventions**: no version-bound types in the main class's fields, method signatures or static initialisers;
  do not `new ModernHooks()`; version implementation classes must not reference each other directly either.
- **From 26.x on, versions are year-based — stop assuming a `1.xx` shape.** Measured on 26.2:
  `matches(">=1.21.9")` and `matches(">=1.21.11")` are both true, while `matches("<2.0")`
  is false — pure semantic comparison treats 26.x as "greater than every 1.x". When writing branches for "the 1.x era",
  do not use upper bounds such as `<2.0`; across such major versions prefer `datapack:` / `resourcepack:` /
  `protocol:` / `world:`, or `Compat`'s fixed capability booleans, which do not depend on the version string's shape.
- **Reliable even at early startup**: during the mixin-plugin stage the Loader may not have registered the `minecraft` container yet;
  `GameVersion` then falls back to reading `version.json` from the classpath for the id.
  Every query is cached after the first call, and missing values return safe defaults (`UNKNOWN = -1` / false) instead of throwing.
- `MinecraftVersions` reads `version.json` from the classpath; if other jars ship the same resource name,
  prefer the copy whose id matches what the Loader reports.

# Build and install

```bash
./gradlew build publishToMavenLocal     # the eight intermediary version nodes
python tools/build_named26.py           # 26.2 official-name (named) adapter jar
python tools/selftest-number/run_selftest.py   # pure-Java regression for numeric input validation (no game launch)
```

The first command goes through Stonecutter/Loom and compiles once per version listed in `settings.gradle`; artifacts land in
`versions/<version>/build/libs/smile_libbox-1.0.26+<version>.jar`. The second cannot use Loom:
26.2 has no intermediary and no refmap, so the script builds the classpath precisely from `26.2.json` (including the
`META-INF/jars/*.jar` submodules of `fabric-api`) and additionally falls back to
`libraries/net/fabricmc/sponge-mixin` for the annotations jar (launchers often leave its `downloads.artifact` empty, and mixin cannot compile without it).
It then uses JDK 26's `javac --release 25` to compile the adapter layer under `named26/src` and three mixins directly against the 26.2 client jar, and assembles
`build/libs/smile_libbox-1.0.26+26.2.jar` on top of the pure-Java part of the 1.20.1 jar; the mixin configs under `named26/resources` are written into the jar
and declared in `mixins` in `fabric.mod.json`. The environment variables
`MC_HOME` / `JAVAC` / `MC_VERSION` can override the paths.

> **Careful when editing `named26/src`**: there is no Stonecutter here, so conditional branches such as `//? if ... {`
> are merely comments to javac — the code "compiles but the logic silently disappears". This once wiped out the whole density-level
> read for the mace, making every mace level 0 and always switching to the one earliest in the inventory. The script now scans
> `named26/src` before compiling and exits with an error if it finds conditional comments; write the 26.2 branches out explicitly.

There is no version-agnostic fallback jar — a jar only loads on the game version it was compiled for. Consumers depend on the coordinate matching their target version:

```groovy
repositories { mavenLocal() }
dependencies {
    modImplementation "smile_libbox:smile_libbox:1.0.26+1.20.1"
}
```

Declare `"depends": { "smile_libbox": "*" }` in `fabric.mod.json`. At runtime put
**the one jar matching the target game version** into `mods/`; a version jar's
`depends.minecraft` is `~<version>` (the 26.2 jar additionally requires `java: >=25`), so a mismatch is rejected by the Loader.
The `+26.2.jar` adapter layer uses official-name descriptors, class version 69, and ships three client mixins written with official names
(`smile_libbox.named26.mixins.json`, `compatibilityLevel: JAVA_25`) with no refmap;
**A fallback jar would not be the same as cross-namespace compatibility.** An earlier `+generic.jar` was exactly that —
the 1.20.1 artifact with `minecraft: "*"` patched into its metadata — and it is gone on purpose: only the `api` package
(zero MC references) is usable that way, while the adapters under `client.compat` remain intermediary-compiled and load
nothing. For 26.2 use `+26.2.jar`.

Smile's toolb is wired up this way (hard dependency); it is itself a **single jar** declaring `minecraft: "*"`,
with zero `net/minecraft` references in the constant pools of all 34 classes, reaching the game only through the
